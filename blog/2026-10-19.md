D1 凌晨 04:13，调查最初看到的是 HTTP 错误、磁盘 I/O 异常和大量数据库连接。沿着活跃会话、进程树和日志追下去，发现 PostgreSQL 正在派生 shell 搜索系统文件；继续反查来源，又串起了公网查询接口、Doris 文件读取、共享 SSH 私钥和多台主机的横向登录。

这次事件已确认 **6 台主机发生异常 root SSH 登录，另有生产主库和从库出现 OS postgres 权限的命令执行**。主库 **44.50 MB、50,124 条逻辑变更正文**已到达受控节点；从库还有 **55.99 MB 的回传网络记录**。这两组数字代表不同证据，不能直接相加成“总泄露量”。

## 2. 整体渗透路线

先抓住三个位置：**APP-TEST 是查询入口所在的测试应用服务器，OPS-1 是取得 root 后的主要跳板，APP-PROD 承载通往主库的管理网关。** 后面的时间线和日志关联都围绕这些节点展开。

```text
公网请求
  │
  ▼
QueryConsole 的 /api/query 缺少服务端认证与授权
  │ 使用服务器自己的 query_service 凭据
  ▼
Doris 查询服务
  ├─ 查询业务与认证相关数据
  └─ LOCAL 读取 BE 节点文件
        │ BE 当前运行身份为 root，root 目录文件已有读取证据
        ▼
疑似获得 KEY-OLD 私钥〔强关联，缺当次 PEM 返回正文〕
        │
        ▼
EXTERNAL-A → root SSH → OPS-1
  ├─ KEY-OLD → 另外五台主机 root
  ├─ cdc_reader → DB-PRIMARY → 逻辑解码 → 结果落盘 OPS-1
  ├─ db_reader → DB-REPLICA 代理 → 配置查询、大响应
  ├─ db_admin〔凭据初始来源未明〕→ DB-REPLICA → OS postgres
  └─ 其他数据库 → 配置与审计样本读取

EXTERNAL-A / 已受控 DB-REPLICA
  │ 调用生产数据库管理接口
  ▼
APP-PROD 上的 Kong → Supabase Meta /query
  │ 使用 Meta 服务端数据库凭据
  ▼
DB-PRIMARY 的 db_admin 会话
  ├─ 跨表搜索密钥等内容
  ├─ COPY PROGRAM → OS postgres 文件扫描
  └─ 从主库访问 APP-PROD 的 Redis → 部分任务与配置读取
```

图中的几种身份应分别理解：请求者的 HTTP 身份、应用连接数据库的账号、数据库服务的 OS 用户，以及 SSH 登录用户。OPS-1 上由 root 启动数据库客户端，不意味着数据库服务器也获得了 root 权限。

本案主库有两条独立路线：**复制账号直接读变更**，以及**管理接口借助受信任应用服务器执行高权限 SQL**。不能把它们合并成“管理员账号从公网直连主库”。

## 4. 入口为什么能被利用

### 4.1 不需要先破解网页登录或数据库密码

最初一个容易误判的线索是：数据库审计里出现了一个像真实员工姓名的账号。后续核对发现，那是应用服务端的预置查询账号，并不表示对应人员实施了操作。

实际调用链是：

```text
POST /api/query
  → 查询助手
  → 规划查询 / 模型生成 SQL
  → 只读 SQL 字符串校验
  → 服务端数据库连接
  → 执行查询
  → 按列名脱敏并返回
```

原代码逻辑节选，函数和身份字段已泛化：

```ts
export async function POST(request: Request) {
  const input = await request.json();
  const question = String(input.question || "").trim();

  // 缺少可信的登录态和权限检查。
  const result = await runQueryAssistant({
    question,
    source: "api",
    requesterId: input.requesterId, // 客户端声明，不是认证身份。
  });

  return Response.json({ ok: result.status === "success", result });
}
```

底层执行使用服务器配置：

```ts
const url = process.env.DB_QUERY_URL || process.env.DATABASE_URL;
const connection = await mysql.createConnection(url);
try {
  const [rows, fields] = await connection.query(sql);
  // 整理结果。
} finally {
  await connection.end();
}
```

这条路线的准确分类是 **未授权调用本来就具备数据库查询能力的服务**。没有证据时，不应把它写成传统的“用户字符串拼接导致 SQL 注入”。即使连接驱动没有注入漏洞，接口仍然会替未授权请求者使用高权限账号执行查询。

调查还发现，同一应用的机器人入口有成员/管理员校验，HTTP 入口却没有调用它。一个入口安全，不能保护绕开它的另一个入口。已保存源码与部署构建产物的关键逻辑吻合，增强了判断；文件 mtime 本身则不是不可抵赖的部署历史。

修复示意，以下辅助函数均需按实际系统实现：

```ts
export async function POST(request: Request) {
  const principal = await authenticateServerSession(request);
  if (!principal) return new Response("Unauthorized", { status: 401 });
  if (!await canQueryApprovedDataset(principal)) {
    return new Response("Forbidden", { status: 403 });
  }

  const input = await parseAllowedQueryInput(request);
  return runApprovedQuery({
    principal,                       // 来自可信会话。
    queryTemplateId: input.templateId,
    parameters: input.parameters,   // 值参数化，不接受任意表/函数。
  });
}
```

服务端要对每次敏感操作和对象归属做授权；隐藏按钮、网页登录、CORS 或请求体里的用户 ID 都不能替代它。[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

### 4.2 “只允许 SELECT”没有限制读取对象

原实现的关键逻辑是字符串检查，节选如下：

```ts
const forbiddenKeywords =
  /\b(insert|update|delete|drop|alter|truncate|create|replace|grant|revoke|merge|call|execute|exec)\b/i;

if (!/^select\b/i.test(compact)) {
  return { ok: false, reason: "Only SELECT queries are allowed" };
}
if (forbiddenKeywords.test(compact)) {
  return { ok: false, reason: "SQL contains a forbidden keyword" };
}
// 后续还有 LIMIT 限制。
```

它约束了部分写入语句，但没有回答：

- 能读取哪些数据库、表、列和系统目录？
- 能调用哪些函数或表函数？
- 能否读取文件、外部资源或认证材料？
- 数据库账号和服务进程分别拥有什么权限？

本案中，`SELECT` 调用了 Doris 的 `LOCAL` 文件表函数，root 目录内容实际被读取。`LIMIT` 只限制返回结果数量，不能证明执行代价小，也不能把少量敏感文件变成安全内容。

当前 Doris 4.x 文档说明 LOCAL 涉及管理员权限和安全目录限制；这些控制应按**实际版本、账号授权和部署配置**核对，不能把当前文档反推成事发版本的配置。现场已证实读取发生，但尚未完整还原当时各项授权配置。[Doris LOCAL 文档](https://doris.apache.org/docs/4.x/sql-manual/sql-functions/table-valued-functions/local/)

### 4.3 按列名脱敏为什么失效

原代码逻辑节选：

```ts
function isSensitiveKey(key: string) {
  return /(password|passwd|pwd|secret|token|api[_-]?key|credential|phone|email|mobile)/i
    .test(key);
}

const redactedRow = Object.fromEntries(
  Object.entries(row).map(([key, value]) => [
    key,
    isSensitiveKey(key) ? "[REDACTED]" : value,
  ]),
);
```

下面用完全虚构的常量说明问题，不读取任何真实表：

```sql
SELECT 'DEMO_ONLY' AS token;
SELECT HEX('DEMO_ONLY') AS h;
```

第一条结果的列名是 `token`，会被遮盖；第二条列名是 `h`，规则不认识，而 HEX 只是可逆编码。真正的缺陷是**任意表达式和别名改变了输出字段名，脱敏规则丢失了字段来源**。同样的问题也出现在把整行 JSON、文件内容或日志放进普通字符串列时。

实际结果中，三个不同的业务令牌通过类似方式返回。另一些带 Key 字样的结果只是配置引用名称，不能算有效密钥。

防护顺序应该是数据库最小权限、安全视图或预定义查询先限定数据，再做输出脱敏。输出正则不应是秘密保护的唯一边界。

## 5. 从文件读取到主机控制

### 5.1 私钥链怎么证实，哪里还缺证据

调查把以下独立线索放到同一条时间线上：

1. Doris 审计显示在 ANALYTICS-1 读取 root 目录的 PEM。
2. 返回 27 行、扫描 1,675 字节。
3. 当前对应旧私钥的大小、行数相同，公钥指纹与后续登录使用的旧密钥一致，统一记为 KEY-OLD。
4. 25 分 45 秒后，EXTERNAL-A 用 KEY-OLD 成功 root 登录 OPS-1。
5. OPS-1 很快用 KEY-OLD 横向登录另外五台。

这些证据高度支持共享私钥是从文件读取路径暴露的，但最关键那次 PEM 响应正文未保存，不能声称已逐字核对“取得的私钥就是这一份”。

### 5.2 Doris BE 运行身份放大了影响

后续复核发现三台 BE 当前均以 UID 0 运行。当前状态与此前 root 文件读取事实共同提示，数据库的文件能力没有被操作系统身份有效收窄。

取证时应读实际进程，而不是只看部署说明。下面是调查方法的整理版，仅读取进程身份：

```bash
sudo ps -C doris_be -o pid,ppid,user,comm
```

若进程名或容器环境不同，先确认真正的服务 PID，再读取 `/proc/<PID>/status` 的 `Uid:`。不要默认打印完整 `args` 或环境变量，它们可能包含连接串和密码。

降权是必要的影响收敛措施，但不能代替 SQL 授权：即使进程不是 root，它仍能读取自身配置和业务凭据。服务专用账号、文件最小权限、禁止存放不必要的私钥副本、SQL 能力限制需要同时落实。

## 6. 数据库的两条路线与三种权限

### 6.1 复制账号能做什么，不能只看 SELECT

主库日志中，复制账号的部分普通表查询和文件读取被拒绝。若调查停在这里，很容易误报“数据库没有被读到”。

但后续发现：逻辑复制槽确实被创建并读取，两份结果已到达 OPS-1。它们包含认证表和业务表的变更，形成独立于普通 SELECT 的取数证据。

这里不能扩大为“复制角色自动等于超级用户”或“所有逻辑复制都绕过 SELECT/RLS”。普通查询、原始复制槽解码、内置发布订阅是不同能力，初始表同步也有单独权限要求。应同时核对角色、输出插件、复制槽与具体读取机制。[PostgreSQL 逻辑复制安全](https://www.postgresql.org/docs/15/logical-replication-security.html)

`peek_changes` 不推进槽消费位置，重复读取可能重复返回；记录数不能直接当用户数。[复制管理函数](https://www.postgresql.org/docs/15/functions-admin.html#FUNCTIONS-REPLICATION)

### 6.2 从库代理为什么让数据库看到 localhost

已确认路线为：

```text
OPS-1 → DB-REPLICA 上的 TCP 代理端口 → 127.0.0.1:5432
```

数据库日志中的 localhost 是代理结果，不代表请求来自本机运维人员。代理日志中的 200 是 **TCP stream 状态**，既不是 HTTP 200，也不是数据库密码认证成功。

判断认证是否成功，需要看到 SQL 执行、明确的认证成功记录或真实结果。对系统文件读取报“权限不足”，通常说明数据库身份已认证，但该功能未获授权；HBA 拒绝则发生在更前面的连接访问控制环节，不能证明密码正确。

### 6.3 Meta 如何借助受信任应用服务器进入主库

这里的 Meta 指 Supabase 的数据库管理服务。

主库拒绝了 OPS-1、从库使用管理员账号的多次直连尝试，但应用服务器是允许来源。管理接口收到请求后，Meta 使用自己的数据库凭据建立连接。

因此：

```text
调用者能调用管理 API
    ≠ 调用者一定知道数据库密码
    ≠ 调用者一定能直接连接数据库
```

本案另有残留脚本证明管理员密码已经被掌握，但这是独立证据。不能仅凭 Meta 执行成功，就说 HTTP 接口一定返回过该密码。

调查保存的网关配置结构如下。只保留路由、认证插件和授权组，没有 Consumer 的凭据；这也不是可直接部署的完整配置：

```yaml
services:
  - name: meta
    routes:
      - name: meta-all
        paths: ["/pg/"]
    plugins:
      - name: key-auth
        config:
          hide_credentials: false
      - name: acl
        config:
          hide_groups_header: true
          allow: ["admin"]
```

Key Auth 识别 Key 对应的 Consumer，ACL 再检查其是否属于允许的 admin 组。`hide_credentials: false` 表示不主动从转发请求中移除 Key，不是关闭认证；`hide_groups_header: true` 影响上游分组头，不是关闭 ACL。[Kong Key Auth](https://developer.konghq.com/plugins/key-auth/)、[Kong ACL](https://developer.konghq.com/plugins/acl/)

| 观察 | 能确认什么 | 不能单独确认什么 |
|---|---|---|
| HTTP 401 | 某层认证或身份检查未通过 | 一定未携带 Key，或一定由 Key Auth 返回 |
| HTTP 403 | 某层拒绝访问 | 已取得管理员 Key |
| HTTP 200 | 收到成功 HTTP 状态 | SQL 全部成功、使用了哪把 Key、Key 的来源 |
| Meta 与数据库日志对应 | 部分请求已进入 SQL 执行通道 | 缺共同 ID 时每条请求的唯一对应 |
| 文件声明 key-auth 和 ACL | 保存的配置具有这些控制 | 事发时始终加载相同配置、没有其他路径 |

现场比对没有命中公开示例 Key，也没有在检查的 Nginx 配置中找到自动注入认证头的指令。这排除了两个具体解释，不能因此证明其他泄露路径不存在。状态码变化本身不证明 Kong 或 Supabase 存在被利用的产品漏洞。原调查还核对了对应版本的 [Kong 2.8.1 Key Auth 源码](https://github.com/Kong/kong/blob/2.8.1/kong/plugins/key-auth/handler.lua)与 [ACL 源码](https://github.com/Kong/kong/blob/2.8.1/kong/plugins/acl/handler.lua)。

### 6.4 COPY PROGRAM 报错，为什么仍然是系统执行

事件中抓到的进程结构经过脱敏后是：

```text
postgres
└─ sh
   ├─ base64
   └─ bash
      ├─ grep
      └─ head
```

PostgreSQL 的 `COPY ... PROGRAM` 是受高权限控制的服务端功能，需要超级用户或相应的 `pg_execute_server_program` 权限，由数据库服务的 OS 用户执行程序，再处理程序输入/输出。本案中，程序输出已经产生，随后 COPY 的列解析报错；进程树、子进程信号与终止日志共同证明命令已经启动。**SQL 最终失败不能撤销已经发生的外部程序执行。**[PostgreSQL COPY 文档](https://www.postgresql.org/docs/15/sql-copy.html)

示意语法仅用于识别日志，命令内容不可执行：

```text
COPY result_table FROM PROGRAM '<脱敏后的系统命令>';
```

它不能单独证明 root 提权。主从库命令结果对应 OS `postgres`，与另外六台主机的 root SSH 控制必须分开统计。

## 7. 溯源过程：从告警逐层找回证据

### 第一步：确认负载在等什么

最初只有 HTTP 错误、磁盘 I/O 图和连接总数。连接很多、idle 很多，并不能直接定位负载；重点是活跃查询时间、事务时间、等待事件和后端 PID。

下面是调查使用过的会话排查方法的脱敏整理版。它只返回元数据和粗分类，不输出可能含秘密的 SQL 正文：

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '5s';
SET LOCAL lock_timeout = '1s';
SET LOCAL TIME ZONE 'UTC';

SELECT pid, usename, application_name,
       client_addr, client_port, state,
       clock_timestamp() - query_start AS query_age,
       clock_timestamp() - xact_start AS transaction_age,
       wait_event_type, wait_event,
       CASE
         WHEN query ILIKE '%COPY%' AND query ILIKE '%PROGRAM%'
           THEN 'program_keyword_candidate'
         WHEN query ILIKE '%pg_logical_slot%'
           THEN 'replication_keyword_candidate'
         ELSE 'other'
       END AS query_class
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
  AND (state = 'active' OR state LIKE 'idle in transaction%')
ORDER BY query_start NULLS LAST
LIMIT 100;

ROLLBACK;
```

关键词分类可能误报，不能替代审阅 SQL。真正的语句只保存在受限证据区。只读事务避免业务写入，但查询本身仍会消耗资源；这里通过系统视图、行数和超时限制范围。

`pg_stat_activity` 不是历史审计，查询文本也可能被截断。进程结束后，应转向持久日志。[PostgreSQL 活动视图](https://www.postgresql.org/docs/15/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW)

### 第二步：把数据库 PID 对到操作系统

进程仍存在时，使用其准确 PID，优先只读命令名而非完整参数：

```bash
# 将 12345 替换成已确认的数据库后端 PID。
sudo ps -p 12345 -o pid,ppid,user,lstart,etime,comm
sudo pstree -p 12345
sudo readlink -f /proc/12345/exe
```

本案看到 PostgreSQL 派生 shell 和搜索程序，调查因此从“慢 SQL”扩展到“数据库系统命令执行”。后来进程被结束，现场快照不能恢复，需要寻找终止日志中保留的完整语句。

### 第三步：日志收集器关闭，不代表没有日志

当时 `logging_collector=off`，`pg_current_logfile()` 为空。真正的 PostgreSQL stderr 被服务启动方式重定向到了发行版管理的日志文件。

先核对设置：

```sql
SELECT name, setting
FROM pg_settings
WHERE name IN (
  'data_directory', 'log_destination', 'log_directory',
  'logging_collector', 'log_line_prefix', 'log_timezone',
  'log_connections', 'log_disconnections', 'log_statement',
  'log_min_duration_statement', 'log_min_error_statement',
  'track_activity_query_size'
)
ORDER BY name;

SELECT pg_current_logfile();
```

在 Debian/Ubuntu 的主机安装场景中，调查使用了下面的定位方法。版本和 cluster 路径需要按 `pg_lsclusters` 实际输出调整：

```bash
sudo pg_lsclusters
sudo sh -c '
  db_pid=$(head -n 1 /var/lib/postgresql/15/main/postmaster.pid)
  ps -p "$db_pid" -o pid,ppid,user,comm
  readlink "/proc/$db_pid/fd/2"
'
```

之后对完整日志副本按时间、PID、错误类型筛选，而不是只 grep 一个报错单行。SQL 和 CONTEXT 可能跨行，原始上下文要保留。`log_min_error_statement=error` 可以留下错误语句；未开启成功语句记录时，无法补出所有成功查询。[PostgreSQL 日志配置](https://www.postgresql.org/docs/15/runtime-config-logging.html)

### 第四步：从数据库来源反查网关与容器

数据库看到 APP-PROD，不等于 APP-PROD 已被 SSH 控制。调查继续查看该机的 Nginx、Kong 和 Meta。

使用过的只读元数据方法，容器名已改为示例名：

```bash
sudo docker inspect db-meta db-gateway \
  --format '{{.Name}} started={{.State.StartedAt}} restarts={{.RestartCount}} log_driver={{.HostConfig.LogConfig.Type}} log_path={{.LogPath}} ports={{json .NetworkSettings.Ports}}'
```

不要直接把完整 `docker inspect` 或 `.Config.Env` 粘到公共讨论里：它可能包含数据库密码和 API Key。网关路由检查只输出路径、认证插件和 ACL 关系；凭据比较在本机内存完成，只返回布尔值。

最终取得三层对应：Nginx 的管理请求、Meta 的请求 ID 与数据库错误、数据库后端中的 COPY 语句。部分只有时间和错误模式相同，应写“强关联”；没有共同 request ID 时，不应声称每条都唯一对应。

### 第五步：确认 SSH 是成功、失败，还是误报

`Invalid user`、`preauth` 关闭、无效协议 banner 都不是成功登录。必须寻找 `Accepted publickey` 或 `Accepted password`，再对照会话结束、账号、源地址与密钥指纹。

本案应用服务器留存日志没有找到已知攻击来源的成功 SSH，但另一个运维节点却有大量 root 成功认证。进一步按 KEY-OLD 追踪，发现五台横向登录。

后续出现使用 KEY-NEW 的成功登录，也不能直接宣布新密钥再次泄露。调查先核对操作者，最终有一组 **72 次当天登录及 229 次历史登录被确认属于内部人员**，从攻击统计中移除。没有逐条时间戳的 shell history 也不能直接归到某个 SSH 会话。

### 第六步：反查查询应用入口，而不是只盯数据库

沿 Doris 审计的数据库账号和客户端地址反查，定位到 APP-TEST 的 QueryConsole，再核对：

1. Nginx 虚拟主机和反向代理目标。
2. 应用进程、部署目录与构建文件。
3. API 路由是否调用授权逻辑。
4. 数据库连接配置是否使用该审计账号。
5. 保存的查询结果是否与审计时间和行数对应。

入口日志显示先批量枚举路径，再对 `/api/query` 调整方法和参数，最终成功执行查询。公开 JS 中找到了默认用户名，却没有找到该查询路径字面量；因此更支持字典枚举发现接口，而不是从 JS 直接抄出接口。

### 第七步：用 SSH、文件时间、数据库代理做交叉关联

两笔从库大响应没有保存正文。调查找到了 SQL 文件、SSH 认证记录和代理会话结束记录，得到如下脱敏关联：

| 文件 | SSH 接受 | 文件 mtime | 从库响应结束 | SSH 关闭 |
|---|---|---|---|---|
| query_01.sql | 02:53:33.017 | 02:53:33.540 | 02:53:39 | 02:53:39.969 |
| query_03.sql | 02:53:53.789 | 02:53:54.310 | 02:54:02 | 02:54:02.911 |

连续五份文件都有约 0.52 秒的同类关系，使“外部通过 SSH 在 OPS-1 发起查询”具有较强证据。数据库报错还精确匹配了部分脚本语句。

但代理日志只有秒级结束时间，主机历史时钟偏差没有单独测量，缺少进程执行审计、共同源端口和 stdout 记录。正确结论是强关联，不能据此生成虚假的完整执行命令。

两份 SQL 没有设置本地结果输出；如果调用端接收 SSH stdout，结果可能根本没有落盘。本地找不到输出文件，不等于查询没执行或调用者没收到数据。

### 第八步：追密码来源时，坚持“同一个秘密值”

调查在调度系统明文数据源和报表系统可解密配置中，找到了与攻击脚本完全一致的普通数据库密码。这为普通账号提供了具体存放位置，但不能拿它证明管理员密码来源。

对管理员旧密码的现存配置检查覆盖了 24,180 行指定字段；加密字段经过授权解密核对，仍未命中。不能只搜索密文无结果就说“没有密码”，也不能用现存阴性结果排除事发后已经删除或修改的数据。

下面是本机精确比较的伪代码，不连接数据库，也不输出秘密：

```python
from getpass import getpass
import hmac

expected = getpass("已轮换的事件凭据，仅在本机内存使用: ")

# candidates 来自授权保存的受限证据；不要打印 candidate 值。
for field_id, candidate in candidates:
    matched = hmac.compare_digest(
        candidate.encode("utf-8"), expected.encode("utf-8")
    )
    if matched:
        print({"field_alias": field_id, "exact_match": True})
```

这只是避免在报告里重新泄露凭据，不是完整的秘密内存保护方案。不要把旧密码作为命令行参数，或拼进可能被数据库审计记录的 SQL 文本。输出只保留字段代号、匹配布尔值、检查范围和时间。

## 8. 证据采集脚本中的工程细节

调查实际使用过一个主机型 PostgreSQL/Linux 只读采集器。它读取已有日志与配置、采集系统元数据、建立本机只读数据库会话，生成证据副本、manifest 和 SHA256。

“只读”是指不改业务数据、日志配置和服务状态；采集仍会创建本地证据文件、使用磁盘和建立数据库会话。不是无资源开销，也不能在未知权限下直接运行。

### 8.1 数据库连接保护节选

```python
env = os.environ.copy()
for key in list(env):
    if key.startswith("PG"):
        env.pop(key)

env.update(
    PGCONNECT_TIMEOUT="5",
    PGAPPNAME="incident-evidence",
    PGPASSFILE="/dev/null",
    PGOPTIONS=(
        "-c default_transaction_read_only=on "
        "-c statement_timeout=5000 "
        "-c lock_timeout=1000"
    ),
)
```

连接使用本机 Unix socket、`psql -X -w`，依赖授权的本机认证，不输入截获密码。原始采集器曾保留有限长度 SQL 片段；这些片段可能含秘密，公开整理版只展示元数据。

### 8.2 文件采集保护节选

下面是 Linux 原采集方法的结构节选，省略复制、异常处理和清单写入，不是完整脚本：

```python
os.umask(0o077)
fd = os.open(path, os.O_RDONLY | os.O_NOFOLLOW | os.O_NONBLOCK)
with os.fdopen(fd, "rb") as source:
    before = os.fstat(source.fileno())
    if not stat.S_ISREG(before.st_mode):
        record_skip("non_regular_file")
    elif before.st_size > remaining_budget:
        record_skip("size_or_space_limit")
    else:
        copy_bounded_and_hash(source, before.st_size)
        after = os.fstat(source.fileno())
        record_source_changed(
            before.st_size != after.st_size
            or before.st_mtime_ns != after.st_mtime_ns
        )
```

实际采集器设置了单文件 256 MiB、总量 2 GiB、至少保留 512 MiB 空闲空间等上限。超限、超时、文件变化和读取失败都会写入 manifest。日志按 mtime 选择后可能整份复制，因此复制到的内容不一定全部属于目标时间窗。

完整性至少核对：原包哈希、文件哈希、成功/跳过数量、时间覆盖、是否截断、是否在采集中变化。SHA256 证明持有的内容是否一致，不证明已失陷主机上的日志从未被修改。

不要默认解压并执行 tmp 目录里的脚本。应先静态列出归档成员，识别绝对路径、`..`、链接和异常体积；需要提取时再制定明确的安全路径策略。

### 8.3 tmp 样本具体做了什么

主库 tmp 归档包含 526 个普通文件，其中 47 个 Python 文件、86 个 shell 文件。调查采用静态分析、结果文件核对和离线公钥匹配，没有重跑这些脚本，也没有用截获的凭据测试线上接口。

| 样本行为 | 代码/结果显示的作用 | 已确认的影响与限制 |
|---|---|---|
| 身份与目录检查 | 查询运行身份、进程及文件，输出到 tmp | 主库存在 OS postgres 权限执行；不是 root 提权证据 |
| 文件和秘密搜索 | shell、grep、编码工具组合，寻找配置和认证材料 | 数据库日志和进程树证实执行；命中关键词不等于获得全部有效凭据 |
| Redis 配置、键名及任务读取 | 未执行 AUTH 就能读取配置、SCAN 和部分值 | 已取得部分任务字段；日志中的 1,078 万是累计键名返回次数 |
| 内网端口与服务探测 | 网段常见端口、少量主机全端口扫描，检查 SSH 和管理服务 | 开放端口只证明可达；不能当作每台都已入侵 |
| 私钥、JWT 和 SSH 尝试 | 包内存在重复私钥与角色声明为管理用途的候选 JWT | 材料存在已证实；JWT 解码不是验签，具体登录成功另看目标日志 |
| 后台任务 | 通过后台进程运行扫描，结果文件记录结束 | 某次扫描完成已证实，不等于已安装开机持久化 |
| Redis 文件位置修改 | 尝试调整保存目录和文件名 | 留存结果是 protected config 拒绝，不能写成已借此写入系统文件 |
| 元数据、SSRF 和其他管理接口探测 | 尝试不同接口、路径和参数 | 只能逐项判断；例如一次 LOCAL 读取 HTTP URL 实际被当成本地路径并失败，不能算成功 SSRF |

Redis 保存结果显示默认用户存在 `nopass` 和广泛命令/键权限，无认证读取也已得到结果。这是**内网可达加过宽 Redis 权限**形成的独立边界失效。个别受保护配置禁止修改，并没有阻止读取任务和配置。修复需限制可达来源、分配业务 ACL 和关闭不必要管理命令；不能把“只能内网访问”当作已经授权。

还有一个重要的版本陷阱：归档中的某个同名 shell 文件在 D1 04:19:19 被修改，内容已经变成主机/SSH banner 探查，与 04:13 数据库日志写入的搜索脚本不同。因此必须用**事发 SQL 中的脚本内容、文件哈希和保存时间**识别版本。不能打开最后留下的同名文件，就断言它代表早先执行的内容；归档 UID 也只说明保存的属主元数据，不直接证明每个文件的创建者。

这些样本明确存在资源消耗行为，但没有按进程测得完整 I/O 贡献。它们支持故障关联，不足以把整段磁盘满载的每一个字节都归给单个脚本。

| 备份解析器约 3.13 GB | 输入计数，不能证明完整备份被导出 |
| Redis 约 1,078 万 | 键名返回次数，不是独立键数量或 value 数量 |
| 约 3,716 万用户 | 表计数结果，不是导出行数 |
| 两张敏感表各 100 行 | 数据库返回行数，原始明文凭据是否通过脱敏层仍不完整 |

**44.50 MB 的结果文本和 55.99 MB 的网络流量不能相加成“总泄露量”。** 同时也不能因为最终互联网传输未查清，就否认受控节点已经取得数据这一事实。

人员确认的正常报表任务累计返回 896,984 行，已从攻击取数统计排除。观察到“成功查询很多”后，要先核实操作者和业务背景。

### 10.1 云初始化文件的实际结论

后续不是只看关键词，而是核对了当前文件和两次保留的历史返回正文：

- 两次历史实例元数据各 92 行，包含实例、系统信息和公钥；管理员密码字段为空，没有云 AK/SK、数据库密码或私钥。
- 初始化脚本确实通过 HTTP 下载脚本后高权限执行，包装脚本没有签名/哈希校验；但没有证据表明发生下载劫持。
- `set -x` 曾把元数据访问令牌打印到权限为 0644 的日志。记录来自更早时间，申请 TTL 为 120 秒，按记录时效已在事件前过期；不是长期云密钥。
- `/proc/1/environ` 的 stat 大小为 0 不等于没有内容；一次 SQL 返回 0 行也不能证明当时环境为空。
- 缓存中的旧公钥不能反推出私钥，也不代表当前 `authorized_keys` 仍授权；云模板是否会重新写入旧授权需要另查。
- 仍缺云控制面角色、云 API 与云助手任务审计，不能据磁盘上没有 AK/SK 就排除实例角色风险。

cloud-init 普通实例数据缓存与敏感数据缓存有不同用途；应根据实际文件内容判断，不能见到 metadata 就认定云凭据泄露。[cloud-init instance-data](https://docs.cloud-init.io/en/latest/explanation/instancedata.html)

检查日志泄漏时只返回计数，不把令牌再次打印出来。以下为整理版：

```python
import re
from pathlib import Path

rules = {
    "assignment": re.compile(r"\bMETADATA_TOKEN=", re.I),
    "header": re.compile(r"X-[A-Za-z0-9-]*metadata-token:", re.I),
}
counts = dict.fromkeys(rules, 0)
with Path("cloud-init-output.log").open(errors="replace") as source:
    for line in source:
        for name, regex in rules.items():
            counts[name] += bool(regex.search(line))
print(counts)
```

这些是出现次数，赋值与请求头可能重复同一令牌，不能当作不同令牌数。[OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

### 10.2 Socket 加房间顺序的代码细节

历史日志显示一个 visitor 加入别人的基础房间，5 毫秒后业务层才拒绝。当前源码存在对应逻辑，节选如下：

```ts
socket.join(sessionId);
const result = await handleCreateSession({ sessionId, user });
if (!result.success) {
  socket.emit("error", "access denied");
  return; // 此分支没有退出刚加入的房间。
}
```

当前源码不必然等于事发镜像，历史日志则确认了这一顺序确实出现。主要模型消息走另一个生命周期房间，不能只看第二连接在线期间模型生成了内容，就认定它收到了内容。

修复示意：先依据服务端身份完成新建/已有会话的对应授权，再订阅；操作失败时只清理本次新加入的订阅，避免破坏既有合法连接。

```ts
const session = await createOrAuthorizeSession(principal, input);
const room = session.id;
const joinedByThisOperation = !socket.rooms.has(room);
if (joinedByThisOperation) await socket.join(room);
try {
  await handleAuthorizedOperation(session, principal);
} catch (error) {
  if (joinedByThisOperation) await socket.leave(room);
  throw error;
}
```

这不是完整修复提交；并发请求、会话生命周期房间和断连清理仍需按真实实现测试。

## 11. 可复用的离线脚本

把完整代码放在下载文件里，正文保留用途和边界。三个脚本均使用 Python 3 标准库，只读取明确指定的本地文件，不联网、不连接数据库、不执行样本。它们是整理后的分析工具，不是原始攻击脚本，也不附带事件日志。

| 工具 | 输入与用途 | 下载 |
|---|---|---|
| Nginx 统计 | combined access log 或 `.gz`；统计状态码、方法、来源代号和固定路径分类 | <a href="/downloads/incident-analysis/nginx_summary.py" download="nginx_summary.py">nginx_summary.py</a> |
| SSH 成功认证统计 | auth 日志或 `.gz`；聚合 Accepted 记录，替换来源、非 root 用户和指纹 | <a href="/downloads/incident-analysis/ssh_summary.py" download="ssh_summary.py">ssh_summary.py</a> |
| 归档静态清点 | tar 及支持的压缩格式；统计成员类型、逻辑大小和可疑路径 | <a href="/downloads/incident-analysis/archive_inventory.py" download="archive_inventory.py">archive_inventory.py</a> |

下载到当前目录后，可对本地证据副本运行，以下文件名均为示例：

```bash
python3 nginx_summary.py evidence/access.log evidence/access.log.1.gz --include-times
python3 ssh_summary.py evidence/auth.log evidence/auth.log.1.gz --include-times
python3 archive_inventory.py evidence/sample.tar.gz --max-members 10000
```

需要分析时间分布时，给 Nginx 或 SSH 工具加上 `--include-times`，输出 UTC 小时分布和可用的时间样本；不加时只输出聚合统计。来源 IP、用户名和密钥指纹使用运行内代号，原始 URL、查询参数和 UA 不进入输出。

Nginx 工具还支持带时区的 `--since` 和 `--until`，按左闭右开的区间过滤。SSH 工具不会猜测缺失的年份和时区，这类记录会计入时间质量统计，但不进入 UTC 小时分布。

使用结果时仍要注意：

- 来源代号只在一次运行内有效，两个工具里的 `SOURCE_001` 不保证是同一来源；真实客户端 IP 还取决于可信代理配置。
- 重复行、重叠轮转文件不会自动去重。读取完成不代表每行都解析成功，要一起看解析失败和未匹配计数。
- UA 只是自动化特征提示，Accepted 也不能独立判断操作者。脚本不是攻击归因工具。
- 归档工具不提取成员、不输出成员名和正文。成员上限不等于解压字节或耗时上限；元数据遍历也不是完整归档校验或安全解压保证。

## 12. 如何把这次经验转成告警

单个 curl UA 不能识别攻击者；正常自动化、监控、失效会话也可能产生 401/403。在敏感期可以先用低阈值建立观察，再结合管理路径、来源身份和失败后成功的序列判断。

按源 IP 统计 5 分钟的 401/403，以下标签均为示例。原始日志应为标准 Nginx combined 格式，行首已经是经过可信代理规则还原的客户 IP：

```logql
sum by (client_ip) (
  count_over_time(
    {namespace="example", app="gateway"}
    | regexp `^(?P<client_ip>\S+) \S+ \S+ \[[^]]+\] "[A-Z]+ /[^ ]* HTTP/[0-9.]+" (?P<status>[0-9]{3}) [0-9]+ `
    | client_ip!=""
    | status=~"401|403"
    | __error__=""
    [5m]
  )
) >= 10
```

按自动化 UA 统计，不直接赋予“恶意”标签：

```logql
sum by (client_ip) (
  count_over_time(
    {namespace="example", app="gateway"}
    | regexp `^(?P<client_ip>\S+) \S+ \S+ \[[^]]+\] "(?P<method>[A-Z]+) [^ ]+ HTTP/[0-9.]+" [0-9]{3} [0-9]+ "[^"]*" "(?P<ua>[^"]*)"`
    | client_ip!=""
    | method!="OPTIONS"
    | ua=~`(?i).*(python-urllib|python-requests|curl/|wget/|sqlmap|go-http-client|libwww-perl|aiohttp|httpx).*`
    | __error__=""
    [5m]
  )
) >= 10
```

这些是查询表达式，不是已导入、绑定通知和验证触发的 N9E 配置。按主机分开统计可改为 `sum by (host_name, client_ip)`。IP、UA 适合查询时提取；不要未经评估把高基数字段做成 Loki 写入索引标签。查询时聚合也需要评估结果序列和告警实例数量。[LogQL 解析字段](https://grafana.com/docs/loki/latest/query/log_queries/#parser-expression)、[Loki 高基数说明](https://grafana.com/docs/loki/latest/get-started/labels/cardinality/)

更高价值的事件还包括：管理路径失败后出现成功、数据库创建异常复制槽、数据库派生 shell、同一 SSH 密钥短时间跨多个节点 root 登录。每类信号都需要已知正常任务清单，否则会把调查人员自己也算进去。

## 13. 处置状态和未解决问题

已证实的处置包括：限制部分管理入口、轮换数据库和 API 凭据、终止一批异常数据库后端、清理部分主机旧 SSH 授权、停用 QueryConsole 并移除自动恢复条目。

安全组曾因后续调查重新开放，不能把一次“已关闭”当作永久状态。主机已经发生 root 或数据库 OS 权限执行后，单纯轮换密码不足以证明可信，需要保全证据、排查持久化与配置变更、撤销凭据副本，并评估可信重建。

仍未闭环的关键问题：

1. 管理员数据库密码和管理 API Key 最初从哪里取得。
2. 两次早期大响应的具体正文，以及是否含管理员凭据。
3. 从受控节点向外部实际传输了哪些数据、多少数据。
4. 全部业务表涉及的用户并集及令牌后续使用情况。
5. 所有受控主机的残留清理、云控制面影响和业务恢复验收。

后续调查应优先寻找能改变这些结论的证据：调用端输出、事发配置版本、完整执行审计、网络传输记录和云控制面操作。重复扫描当前文件而没有扩大证据范围，不能把未知逐步变成确定。
